# Kurumi 循环式 Agent 设计

## 目标

Kurumi 接收持续到来的玩家消息，综合未完成任务、工具反馈、历史对话与变量，由模型决定下一步行动，直到模型明确 `finish`。脚本结束仅表示一个执行阶段结束，不代表任务完成。

## 关键行为

- 所有符合现有唤醒规则的消息都进入有序队列；执行期间不丢消息。主人发出的 `停止` 或 `/kurumi stop` 仍立即生效，不进队列。
- 下次模型决策将未处理消息整体纳入上下文，由模型判断合并、改优先级、取消或回应；不在 Minecraft 客户端并行执行两个会互相干扰的世界动作。
- 每段脚本可以 `observe(value)` 主动将结构化工具结果回传模型并让出执行控制；若脚本自然结束，也回传完成/失败状态，由模型决定继续或 `finish`。
- `talk(value)` 仅负责公屏发言，长内容由模型拆分多条；不再把公屏的 120 字符上限用作观察数据上限。
- 变量字典不设固定个数上限，在同一 Agent 任务跨阶段保留；保留合理的内存预算、单项容量约束和超时防止客户端卡死。
- 保留最近原始对话、当前任务与决策摘要、近期精细工具结果、较旧工具结果的摘要/按需查看索引，以及当前变量清单。大量背包/箱子数据支持分片读取，不要无声截断。
- `finish` 只有在任务已完成且已经处理当前队列时才生效；资源预算耗尽、断线或停止属于中断而不是完成。
- 延续白名单解释器、NeoForge 26.2、现有主人授权控制与 Web 监测面板。

## 不做的事

- 不实现任意 Java/Python 执行或无限 CPU/内存使用。
- 不在这次改造中替换现有 Baritone、容器和战斗桥接行为。

## 路线对比

1. **推荐：原执行器增加有序 Agent 循环和上下文管理。** 复用现有脚本 AST、结果验证、Web 面板与模型协议，改动集中、兼容旧脚本。
2. 新写一套通用函数调用框架。可扩展性更好，但会重写大量现有动作桥接和校验，风险大。

选第一种。模型决定普通完成时间，但本地保留独立的安全边界。
